# 聊天可靠性补充（2026-10-23）

## 本次改动

- 共享 SSE 解析：公开聊天与调试聊天使用同一解析器，校验 runId、开始事件、运行终态和 stream.done，拒绝混入其他运行的事件、重复终态及终态后的消息。保留中文、Emoji、CRLF 跨块处理及未完成事件缓冲上限。
- 断流恢复：已知 runId 时查询原运行。已完成则恢复保存的回答，仍在执行则保留部分回答并提供查询按钮；失败或取消后需重新发送。未知 runId 的可重试请求复用原幂等键及请求体。
- 错误分类：429 遵循 Retry-After，401/403 不提供重试入口。网络错误、服务端错误仅在持久化运行链路提供重试；409 携带原 runId 时转为查询。
- 访客身份绑定：Cookie 缺失、被篡改或与请求携带的会话标记不匹配时返回 401，不在执行接口静默创建新身份。
- 调试信息：PreviewChat 使用每次请求独立的运行 ID、工具结果、用量及耗时，避免异步回调读取旧 React 状态；保留本地消息 ID 以便后续错误更新。
- 渠道准入：新增单实例、每渠道并发限制，超限返回 429 和 Retry-After；查询及取消不占用执行额度。

## WEB 协议兼容性

1. 先调用公开应用信息接口，浏览器接收签名 HttpOnly Cookie，并保存响应中的 sessionId。
2. 后续执行、查询和取消请求同时携带 Cookie 和 `X-Visitor-Session: <sessionId>`；跨域请求需携带 credentials。
3. 同次请求重试保持原幂等键、请求体和会话标记。若 Cookie 丢失或被另一页面更换，旧请求返回 401，需要重新打开应用。

sessionId 是请求与访客身份的绑定标记，不能替代签名 Cookie。API Key 渠道仍使用原有 Bearer 凭证及 visitorId 范围。

**部署要求：前后端同步发布。** 新 Go 服务会拒绝缺少 X-Visitor-Session 的旧 WEB 客户端。CORS 已允许该请求头，并暴露 X-Run-Id、Location、Retry-After、Idempotency-Replayed。

## 配置与边界

`GO_PUBLIC_MAX_CONCURRENT` 默认 4，范围 1–256，控制单渠道在单实例上的并发执行数，同时受全局并发上限约束。额度在请求结束后释放。这不是分布式配额，也不是按访客计费或限额。

本次没有数据库结构迁移，不改变现有运行开关。恢复查询不意味着断线后必定继续生成，最终以服务端保存的运行状态为准。

### 后续边界修复

- 在取得响应头前停止请求，也保留原 Submission 与幂等键。此时无法查询未知 runId，但可通过“重试本次请求”复用原请求，避免丢失恢复路径。旧链路仍不展示幂等重试。
- 共享 SSE 解析器在派发事件前核对 X-Run-Id 与事件 runId，防止错误事件覆盖用于恢复查询的运行身份。无该响应头的旧链路保持原有流内校验。
- Retry-After 支持整数秒和 HTTP 日期，不再把超过 60 秒的服务端等待要求缩短为 60 秒；无效或过期值使用 1 秒退避。
- 正常接收到 run.failed 后恢复输入原文，便于修改后重新发送；这属于新运行，不伪装成原运行重试。
- test:public 纳入运行管理测试。前端自动测试增至 13 项，类型检查及生产构建通过。本轮未修改 Go，未重复跑后端负载，也未进行浏览器点击验收。

人工复现场景：fixture 发送“响应头延迟”，在 3 秒内停止，再点击“重试本次请求”；应恢复原回答，不新增第二组消息。同一 fixture 的“取消测试”可验证断流后取消。

## 2026-11-01：页面刷新恢复

- 公开页面对持久化运行使用同一浏览器标签的 `sessionStorage` 保存一条未终态请求：发布 slug、幂等键、运行 ID、会话 ID、原消息、创建时间和当前回复位置。
- 页面刷新后先用原访客 Cookie 与会话标记查询已保存的 Run。已完成则恢复服务端回答；运行中保留查询与取消入口；已失败或已取消则恢复原输入，供用户编辑后新发。
- 若刷新发生在取得 `X-Run-Id` 之前，页面保留同一个幂等键，只提供“重试本次请求”，不声称可以查询未知运行。身份失效、运行不存在、运行终态和“新会话”都会清理恢复记录。
- 恢复数据只保留 10 分钟，按公开 slug 隔离；格式非法、超期或存储不可用时安全降级为新会话。它不保存完整聊天记录，也不跨浏览器恢复。

本轮新增恢复存储测试，`test:public` 共 16 项自动测试通过；类型检查及生产构建继续作为发布前检查。运行本身仍与当前 HTTP/SSE 连接绑定：这项前端恢复只解决刷新后查询已有 Run，不能替代后续“执行器与连接解耦、事件持久化、Last-Event-ID 续传”的服务端改造。

## 2026-11-03：发布渠道策略执行

- Go 公开入口现在读取并执行发布渠道配置，而不再只展示在管理页面：WEB 的 `allowAnonymous=false` 会关闭匿名公开访问；WEB/API 的 `allowedOrigins` 会校验带有 `Origin` 的浏览器请求；API 的 `allowedIps` 支持单 IP 与 CIDR。
- API IP 策略只使用 TCP 直连地址 `RemoteAddr`，不读取 `X-Forwarded-For` 或同类请求头，避免客户端伪造来源地址。若部署在反向代理后，需要在可信代理层完成来源校验，或后续显式引入受信代理配置后再解析转发地址。
- 没有 `Origin` 的服务端 API 调用不受来源策略拦截；来源不是 API Key 的身份验证手段。空白名单维持历史兼容行为，即不额外限制。
- 全局 `CORS_ORIGIN` 仍是实例级前置条件：浏览器来源必须先通过全局 CORS，再通过渠道白名单。渠道配置不能绕过未配置的全局 CORS。
- API 渠道的 `rateLimitPerMinute` / `rateLimitPerDay` 已以数据库 UTC 分桶实现原子计数。额度预留与新 Run、会话、消息写入共用同一事务：幂等重放不重复扣额，后续写入失败会回滚额度。命中上限返回 `429` 和 `Retry-After`；查询和取消不占用额度。默认值与管理端一致，为 60 次/分钟和 1000 次/天。
- 新增迁移 `20261104090000_add_publish_channel_quota`。Run Reaper 每小时会清理超过 2 天的分钟桶和超过 90 天的日桶；多实例同时清理是幂等的。高吞吐场景仍可在后续替换为 Redis 的过期计数器。

验证：新增 Go 单元测试覆盖 WEB 匿名开关、来源匹配、IPv4 CIDR、IPv6 单 IP、非法规则和缺失端口；临时 PostgreSQL + 实际 Python Runtime 的公开路由集成测试覆盖 API 来源/IP 拒绝与放行、WEB 匿名关闭、身份、幂等、取消、工具链、事务内配额和回退。未启用 30 秒持续负载开关。
