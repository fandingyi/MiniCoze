# 第六天：运行生命周期与可观测性

日期：2026-10-16。

## 本次改造

在第四、第五天持久化运行的基础上，补齐停机、超时、状态检查失败、慢客户端以及失败运行的用量记录。正式业务默认仍走旧链路，本次没有自动修改数据库或切换环境配置。

### 取消与停机

- 主动取消先提交 CANCELLED，再关闭当前执行连接；其他实例通过数据库状态轮询感知取消，默认间隔一秒。完成与取消仍以数据库中先提交的终态为准。
- 运行期间持续检查归属和账户状态。成员资格撤销或账户停用时停止执行；连续三次状态查询失败也停止执行，避免长时间无法确认运行状态却继续调用模型。
- 收到中断或 SIGTERM 后拒绝新运行，关闭当前 Go → Python 连接，保存 SERVICE_SHUTDOWN 失败状态，并等待 HTTP 请求收束，最长 20 秒后强制关闭连接。
- 强杀、断电和数据库持续不可用不能保证即时落库，仍由截止时间与回收任务收束。没有自动重跑模型，也没有实现执行检查点恢复。

### 分层预算与错误分类

| 层级 | 约束 |
| --- | --- |
| Go Run | 默认 120 秒，可由 GO_RUN_TIMEOUT 缩短，不能超过 120 秒 |
| Python 执行 | 根据本次 Run 剩余预算下发，最多 110 秒，并预留持久化时间 |
| Python 模型连接 | 连接超时 5 秒，读取超时 30 秒；外层总预算仍生效 |
| Go 等待 Python 响应头 | 10 秒，失败标识 RUNTIME_HEADER_TIMEOUT |
| 工具 | Go 数据库事务最多 5 秒，Python 网关请求超时 6 秒；工具超时单独标识 TOOL_TIMEOUT |
| SSE 下游写入/flush | 每次最多 10 秒，flush 错误传回调用方并中止执行 |
| Go 并发准入 | 默认每实例 32，GO_RUN_MAX_CONCURRENT 可配置为 1–256；无等待队列 |

Python 整体预算耗尽与模型读取超时目前都归类为 MODEL_TIMEOUT；Go 总预算耗尽归类为 RUN_TIMEOUT。CLIENT_DISCONNECTED、CLIENT_WRITE_FAILED、RUN_ACCESS_REVOKED、RUN_STATUS_UNAVAILABLE 与 SERVICE_SHUTDOWN 区分不同收束原因。

截止时间同时受数据库记录和本机请求开始时间约束，数据库时钟偏差不能延长本机执行预算。运行数据库连接统一 UTC。

### 有界回收与缓冲

- 过期回收改为每批最多 100 条，使用 FOR UPDATE SKIP LOCKED，不因其他执行器持有一条记录而阻塞整批。每 15 秒继续回收；积压很多时需要多批完成。
- Python 模型 SSE 改为有界字节解析，未收到换行符时也检查长度，防止 aiter_lines 无限累积一条不结束的行。单行最多 1 MiB，临时缓冲上限 2 MiB，跨网络块的 UTF-8 内容保持完整。
- 保留工具参数、工具响应、消息累计长度、轮数和工具次数限制；不是无上限地缓存全部事件。

### 分轮用量与日志

- 新增 AgentModelRound 表。Python 每完成一轮模型响应，发送内部 model.round.completed 回执，包含轮次、耗时、结束原因和供应商用量。
- Go 校验并立即保存回执，然后继续工具或下一轮模型执行。后续运行失败或取消，不删除已保存的回执。重复回执不能重复累计，冲突内容被拒绝。
- 新增 `GET /api/agent-runs/{runId}/metrics`，复用用户鉴权与 Run 归属校验，返回运行耗时、已记录轮次、工具次数、reportedUsage 和 usageComplete。
- reportedUsage 只累加供应商已返回的数据；全部缺失时为 null。usageComplete 仅在运行成功、轮次连续、每轮用量均已返回且最终为文本结束时为 true。失败运行和未知用量不会被伪装成零消耗或完整账单。
- 尚未结束的模型轮次可能已经消耗 token，但没有收到回执；服务或连接中断时也可能丢失尚未确认的用量。因此这些数据用于运行观测，不能替代供应商账单。
- Go 使用 JSON 结构化日志，记录 run_id、接收/重试、终态、错误分类、耗时、模型轮次及回收数量。Python 记录相同 run_id 的开始、终态和中断日志。日志不写提示词、输出正文、工具参数、模型响应或密钥；来自 Runtime 的错误码先经过白名单处理。
- model.round.completed 是内部事件，不转发为前端聊天事件。原先的最终 usage 字段兼容保留。

## 迁移与启用

1. 按现有 Prisma 部署流程应用此前迁移和新增 `20261016093000_add_model_round_metrics`，再生成 Prisma Client。Go 启动会检查新表，不会自行建表。
2. 同步部署 Go 与 Python；旧 Go 不识别新增内部事件，不能只更新 Python 后继续连接旧的 Go 持久化入口。
3. 保持第五天的服务地址与内部密钥配置；按需要设置 GO_RUN_TIMEOUT 和 GO_RUN_MAX_CONCURRENT。默认 GO_PERSISTED_RUNS 仍为 false。
4. 通过持久化草稿调试运行一次请求，再用同一登录身份查询 Run 和 metrics。开发代理已包含 metrics 路由。
5. 回退前停止准入并收束在途运行；保留新增表，不执行破坏性降级。

第三天无持久化预览和 NestJS 桥接仍保留原有迁移边界，不能把持久化链路的新功能视为旧链路也已全部支持。
